Where the Edge Went

Six months, 87 bets, 860 assets scored every cycle. The system reported an average win probability of 63.7% and delivered 44.1%. The gap is not a tuning problem — it is the architecture working as designed.

01

The verdict

This project is carefully built and not carefully designed. The engineering is real: clean module boundaries, typed dataclasses, async orchestration, config-driven parameters, model persistence, a working Streamlit dashboard, a consistent cash ledger. Someone paid attention.

But almost all of that care went into the plumbing, and almost none into the one question that decides whether the system can ever work: is the number I call a probability actually a probability? It isn't. Six estimators produce six differently-scaled scores for the same event, get averaged into a number centred on 50, and that number is fed straight into Kelly sizing as if it were calibrated. Everything downstream is a well-made machine turning a meaningless input into confident output.

The system cannot report “no opportunity.” On any given cycle, 23% of the 860-asset universe scores above the 60% auto-bet threshold, and the top-ranked asset always reads 67–72%. That output is guaranteed by the architecture whether or not any information exists.

The good news is buried in the same data, and it is genuinely good: the ranking carries signal even though the scale doesn't. Realized win rate rises monotonically across the score bands — 27.3%, 41.7%, 45.0%, 56.7%. The top band earned +2.35% on turnover; the bottom band lost 2.73%. There is something here. It is being drowned by a threshold set nine points too low on a scale that doesn't mean what it says.

02

What the ledger says

87 bets between 8 October 2025 and 11 March 2026, closed through 9 April 2026. Total realized P&L +$216.92 on $41,943.66 of turnover — a return of +0.52% on capital deployed, over six months, against a starting bankroll of $10,000. The cash ledger reconciles to the cent; the strategy does not.

03

The one design error everything follows from

A bet in this system is: buy, exit at +5%, stop at −3%. Whether it wins is a first-touch double-barrier event — which price level gets touched first. For an asset with no drift, that probability is fixed by the barrier geometry alone:

P(touch +5% before −3%) = 3 / (5 + 3) = 37.5%
Independent of volatility. Independent of the asset. Expected value at 37.5% is exactly zero — as it must be for a coin flip.

So 37.5% is the neutral line, not 50%. The entire threshold apparatus — the hard 50% floor in trading_system.py, min_probability: 55.0, auto_threshold: 60.0 — is anchored to a number that has no meaning for this payoff. A genuine 45% first-touch probability would be a strong, tradeable edge. The system would reject it and instead demand 60% from a scale that is not measuring the same event at all.

And nothing in the codebase estimates that event. Look at what the models are actually trained to predict:

  • Random Forest / SVM — label is Close.shift(-5)/Close - 1 > 0.03: a fixed 5-bar terminal return. Not a path, not a barrier, no stop.
  • Regression / LSTM — a point forecast of 5-bar return, squashed through norm.cdf(r/0.02) or sigmoid(10r). That estimates P(return > 0), a different question, and the squash saturates so hard that LSTM returns above 60% on 84.7% of all calls (regression); the LSTM had the same defect, visible once its BLOB-corrupted rows were repaired.
  • SMA / RSI — hand-assigned point scores (sma_signal * 25, momentum * 20, …) summed to a 0–100 number. Not probabilities in any sense, and structurally contradictory: one is a momentum rule, the other is mean-reversion.

The realized 44.05% win rate sits 6.5 points above the 37.5% baseline — z = +1.24, which at n = 84 is indistinguishable from no edge at all. Meanwhile the average bet is held 18.8 days while every model predicts 5 bars ahead.

05

How the loss actually accumulates

The stages below are the real pipeline, in order. Each one degrades the signal, and by the end there is nothing left to bet on.

1

The label

Should
Predict which barrier is touched first, within a bounded holding period.
Does
Predicts a 5-bar terminal return crossing +3%. Path-independent, stop-free, and 5 bars against an 18.8-day average hold. The model is answering a question nobody bets on.
2

The estimator

Should
Emit a probability whose value matches observed frequency out of sample.
Does
Emits hand-weighted scores (SMA, RSI), saturated sigmoid squashes (regression at 78.1% mean), or predict_proba from a class-rebalanced model trained on randomly shuffled overlapping windows. Nothing is ever compared against outcomes.
3

The ensemble

Should
Combine estimators by demonstrated out-of-sample skill.
Does
Averages 4.5% and 78.1% with frozen equal weights into a number centred on 50.1% with σ 10.7. The adaptive-weighting machinery is a stub that has never run.
4

The selection

Should
Bet only where the estimate clears break-even with margin.
Does
Takes the argmax of 860 noisy scores every cycle — the pick with the largest positive noise, not the largest edge. 195 of 836 assets clear the 60% gate on a normal cycle, so the gate filters nothing.
5

The sizing

Should
Scale with edge, shrink to zero as edge vanishes, and price in fees.
Does
Applies a mismatched Kelly form, then a 0.25 multiplier, then a 10% cap that binds on half of all bets — and a min_bet_amount floor that overrides the cap downward: max(min_bet, min(kelly, max_bet)) bets $100 when Kelly says $20.
6

The execution

Should
Exit at the barrier, so the designed 1.667 payoff ratio is the realized one.
Does
Polls daily closes when the process happens to be alive. Realized payoff ratio 1.287. This alone moves break-even from 37.5% to 43.7% — 6.2 points of required win rate, which is more than the strategy's entire measured edge.
7

The feedback

Should
Compare every prediction to its outcome and correct the estimator.
Does
Nothing. algorithm_performance: 0 rows. Meanwhile the README already prints “44.4% current win rate” as a feature, one line away from the break-even number that would have exposed the problem six months ago.

07

The redesign

Nothing below requires abandoning the codebase. The module boundaries are sound; what has to change is what flows through them. Ordered by expected effect on P&L.

A

Build the backtester first, and make it the gate

An event-driven bar-by-bar simulator that replays the actual bet: entry with fees, both barriers, the time barrier, intraday high/low for touch detection, and the same code path the live system uses. Run it walk-forward across the whole universe.

This turns 87 live observations into hundreds of thousands of simulated ones, and turns every question below from an argument into a measurement. Nothing else on this list should be attempted before it exists.

Prerequisite for verifying everything else
B

Replace the six scores with one calibrated first-touch model

Label the data the way the bet actually resolves — the triple-barrier method. For every historical bar, walk forward through intraday highs and lows and record which came first: WIN (upper touched), LOSS (lower touched), or EXPIRED (neither, within the max hold). Three classes, and the third one matters: it is the outcome the current design pretends can't happen.

  • Use stationary features only — returns, volatility ratios, cross-sectional z-scores, distance-to-MA in σ units. No raw price or SMA levels; those are what break generalization across assets and currencies.
  • Train one model on the pooled cross-section with purged, embargoed walk-forward CV — overlapping label windows must be purged from the training fold or the score is fiction.
  • Fit isotonic calibration on held-out folds and ship a reliability curve as the release gate. If predicted 60% doesn't deliver 60% ± a few points out of sample, the model does not go live.
  • Drop class_weight='balanced', or calibrate after it — it is currently inflating predict_proba away from the true base rate.
  • Keep SMA, RSI, MACD and the rest — as features into that one model, not as six voters averaging incompatible scales.
Makes every threshold in the system mean something for the first time
C

Guarantee the exit at the venue, not in your loop

The payoff ratio is the strategy. Right now uptime determines it. Two options, in order of preference:

  • Bracket orders. On entry, submit an OCO pair (take-profit + stop) to the broker. The exit is then enforced by the exchange whether your laptop is on or not. This is the real fix.
  • A persistent monitor on intraday bars as a fallback — a separate always-on process, not a step inside the 30-minute trading cycle.

Either way: record realized slippage per exit (barrier price vs. fill) as a first-class metric, and feed the measured distribution back into the backtest so simulated payoffs match live ones.

Recovers ~6.2 points of required win rate — more than the strategy's entire current edge
D

Scale the barriers to each asset's own volatility

Set the barriers in units of the asset's realized volatility over the intended hold — win at +k·σ_h, loss at −m·σ_h — instead of a flat ±5%/−3% for everything from a meme stock to EURGBP. Keeping k/m fixed keeps the payoff ratio and the expected time-to-touch comparable across the universe, which is what makes a single pooled model legitimate in the first place.

Add a hard time barrier (e.g. 15 trading days) that force-closes at market. No bet should be able to sit open for 4.6 months.

Fixes dead capital and makes one model valid across 860 assets
E

Stop betting the argmax of 860 noisy scores

The maximum of many noisy estimates is dominated by estimation error, not edge — the winner's curse, and it is measurable here: the top pick sits a reliable +2σ above the cross-section every cycle regardless of information.

  • Shrink each score toward the cross-sectional mean in proportion to its unreliability (empirical Bayes), then threshold the shrunk value.
  • Require persistence — the asset must clear the threshold on two consecutive cycles, which filters single-cycle noise spikes cheaply.
  • Spread across the top-k rather than concentrating on the single top pick, where the curse is worst.
  • Set the gate against calibrated break-even plus a margin, computed from current fees and measured slippage — not a hand-set 60.
The 66%+ band already returns +2.35% on turnover vs. +0.52% overall
F

Fix the Kelly form, then let it actually bind

For a bet that risks a capped fraction of the position, the growth-optimal fraction is f* = p/l − q/w, not (bp−q)/b. Fold fees in first: w_net = w − 2c, l_net = l + 2c. At 0.25% per side that moves break-even from 37.5% to 43.75% before any slippage — a 6-point effect currently missing from the EV calculation entirely.

  • Note that the corrected formula is unbounded for capped-loss bets — at p = 0.6 it recommends 12× capital. The fractional multiplier and position cap stop being cosmetic and become the actual risk control, so justify them explicitly rather than letting max_bet_fraction silently do all the work.
  • Make min_bet_amount a don't-bet threshold, not a floor that overrides the cap upward.
  • Divide by concurrent slots and apply a correlation haircut — 30 simultaneous long equity bets are close to one leveraged index bet.
Turns sizing from decorative into a real function of edge
G

One source of truth for money

Delete self.active_bets as an authority. Derive open positions, exposure and equity from the database on every read — a SQL view over bets and cash_transactions — so there is exactly one definition of "what do I own". Mark positions to market on every cycle so unrealized P&L is real. Move currency conversion down into the data layer so every consumer, including the trading core, sees USD. Derive asset_type from the symbol. Cast floats before insert.

Then reconcile: a startup check that asserts cash + Σ(marked positions) == Σ(cash_transactions) and refuses to trade if it doesn't.

The headline number stops being wrong by 9×
H

Make the dashboard show the truth, not the score

The UI is the most fixable part of this and currently the most misleading, because it renders an uncalibrated score in a column labelled "Probability" with nothing to compare it against.

  • Draw the break-even line on the same axis as the probability. One horizontal rule at the fee- and slippage-adjusted break-even, so a 62% reading can never again be mistaken for an edge. This is the highest-value pixel on the page.
  • A permanent reliability panel — predicted band vs. delivered win rate, exactly the chart above, computed live from bets. It should be impossible to run this system for six months without seeing that gap.
  • Show probability with an interval, not three decimal places. Three decimals on a number this uncertain is false precision, and it is doing real persuasive work.
  • A slippage column on closed bets: designed exit vs. actual fill, in basis points. Make the −18% stop visible the day it happens.
  • Replace Market Opportunities ranked by raw score with a ranking by expected value after fees, and show assets below break-even greyed rather than hidden — seeing 800 rejected assets builds the right intuition.
  • Structurally: extract a repository module for all SQL, build the CurrencyConverter once behind st.cache_resource, wrap query functions in st.cache_data, and split the 2,343-line class into per-tab render modules.
Turns the dashboard from a confidence amplifier into an instrument
